## 0단계 — 사전 확인 (코드 없음). **여기서 막히면 설계를 다시 한다**

### ① Storage가 `.html`을 인라인으로 그리는가

`Content-Disposition: attachment`로 떨어지면 "새 탭으로 연다"(D2)가 성립하지 않는다.
대시보드에서 `class-bundles` 버킷에 `index.html`과 `images/a.png`를 손으로 올리고
공개 URL을 **새 탭에서 연다.**

- HTML이 **그려지는가** (다운로드되지 않는가)
- `<img src="images/a.png">` 상대경로가 **뜨는가**
- 응답 헤더 `content-type` / `content-disposition` /
  `x-content-type-options` / `cache-control`

### ② 어드민에 실제 로그인 세션이 있는가

**이 작업의 최대 리스크다** → [02-현황분석.md](02-현황분석.md) §4.
`ADMIN_DEV_BYPASS`가 켜져 있으면 `is_admin()`이 항상 false라 **Storage 업로드가
RLS에 막힌다.** 어드민에서 기존 `ImageUpload`(과정 이미지)로 이미지 하나를 올려
보면 즉시 판별된다 — 실패하면 인증 배선이 선행돼야 한다.

둘 다 확인돼야 1단계로 간다.

## 4단계 — 업로드 위젯

새 파일 `src/components/admin/content/bundle-upload.tsx` (`"use client"`).
`html-upload.tsx`·`image-upload.tsx`의 생김새를 따른다.

```
zip 선택 → arrayBuffer → unzip(메모리) → planBundle()
  → 실패면 이유를 role="alert"로 띄우고 중단 (아무것도 안 올린다)
  → 성공이면 uuid = crypto.randomUUID(), path = `${uuid}/`
  → 파일별 upload(`${path}${to}`, blob, { contentType: mime, cacheControl })
     · 동시 4개 정도로 제한. 순차면 파일 50개에서 체감이 나쁘다
     · 하나라도 실패하면 중단하고 에러. 이미 올라간 것은 고아로 남는다
       (01 §6 — DB에 경로가 안 들어가므로 화면에는 영향 없다)
  → onChange(path, zipFileName, fileCount)
```

- 진행 표시 "12 / 48"(A2), 이미 있으면 파일명·개수·**제거 버튼**(A3·A4)
- `accept=".zip"`, 선택 후 `input.value = ""`(같은 파일 재선택)
- 탭 타겟 44px, 에러는 `role="alert"`
- **업로드는 저장이 아니다.** "저장을 눌러야 반영됩니다" 문구를 붙인다
- `HtmlUpload`에도 안내 한 줄 — "파일이 여러 개면 아래 상세 번들을 쓰세요"(요구사항 §4)

### 5-1. 폴더 삭제는 재귀 순회가 필요하다

`storage.list()`는 **재귀가 아니다.** 번들에는 `images/` 같은 하위 폴더가 있으므로
한 번 호출로는 다 못 지운다.

```
list(prefix) → 항목 중 id === null 인 것이 하위 폴더다 → 그 prefix로 다시 list
              나머지는 객체 → 전체 경로를 모은다
모은 경로를 remove(paths) 로 한 번에 지운다 (호출당 개수 상한 주의)
```

- `id === null`이 폴더를 뜻한다는 것은 Storage API 동작이다 — **`context7`로 확인**
- `removeBundleFolder`는 진입 즉시 `BUNDLE_PATH_RE`로 한 번 더 막는다(방어선 2겹)

### 5-2. 액션 — 순서가 중요하다

```ts
function resolveBundle(i: BundleIntent): { path: string; name: string } | undefined {
  if (i.kind === "keep") return undefined;          // 키를 안 넣는다 → 컬럼 안 건드림
  if (i.kind === "remove") return { path: "", name: "" };
  if (!BUNDLE_PATH_RE.test(i.path)) throw new Error("번들 경로가 올바르지 않습니다.");
  return { path: i.path, name: i.fileName };
}
```

`update`의 순서는 **① `get(id)`로 옛 경로 확보 → ② DB update → ③ 성공한
뒤에만 옛 폴더 삭제**다. **거꾸로 하면 안 된다** — 먼저 지우고 update가
실패하면 살아 있는 번들이 사라진다. 이 순서면 최악이 고아 폴더(무해)다.
`deleteRegularClass`도 지우기 전에 경로를 읽어 폴더를 정리한다.
`setRegularClassPublished`는 부분 patch라 **태우지 않는다**.
