## 2. 문서와 다르게 구현한 것 — **여기가 현행이다**

앞 문서(01·03·05·06)는 착수 전에 쓴 것이라, 아래 항목은 이 문서가 우선한다.

### 검증 유틸

1. **`walkBundle`을 `course-bundle.ts`에 추가했다.** [05](05-구현계획.md) §3의 API 목록에
   없던 함수다. 폴더 재귀 삭제(§5-1)를 리포 안에 인라인으로 쓰면 테스트가 안 되므로,
   lister를 주입받는 순수 함수로 뽑았다. Supabase를 모른 채로 남는다
2. **루트 접두사 밖 파일 · 확장자 없는 파일은 조용히 버리지 않고 파일명을 찍어 거부한다.**
   [03](03-보안판단.md) §4의 "조용히 건너뛰지 않는다"를 그대로 확장했다.
   `mysite/index.html`과 루트의 `logo.png`가 섞인 zip은 **거부된다** — 어느 파일이
   문제인지 메시지에 나온다
3. **`./index.html`은 정규화가 아니라 거부.** [06](06-검증체크리스트.md) §1이
   "둘 중 하나로 정해 테스트에 박는다"고 한 항목의 결론이다. 정규화는 "무엇이
   안전한가"의 판단을 한 겹 늘리고, 정상적인 zip은 이런 이름을 만들지 않는다
4. **`walkBundle`에 깊이 10 제한과 방문 집합**을 뒀다(§5-1엔 없음). 이상한 lister가
   순환을 만들어도 멈춘다

### 서버 액션 · 리포

5. **`update`에서 `bundleIntent`가 `keep`이면 `get(id)`를 부르지 않는다.**
   [05](05-구현계획.md) §5-2는 "① `get(id)`로 옛 경로 확보"를 무조건으로 적었지만,
   `keep`이면 지울 대상이 없어 결과를 쓰지 않는다. 매 저장마다 왕복 하나를 더 태울
   이유가 없다. **삭제 경로의 순서(update 성공 → 그 다음 삭제)는 그대로다**
6. **폴더 삭제를 `discardBundleFolder(path, keep)` 헬퍼로 뽑았다.** `update`와
   `delete`가 "빈 경로 스킵 + 실패 삼킴"을 똑같이 필요로 한다. **실패를 삼키는 것이
   의도다** — 남는 건 아무도 참조하지 않는 고아 폴더인데([01](01-요구사항.md) §6),
   그걸 이유로 "저장 실패"를 보여주면 사용자가 실제로 저장된 것을 되돌리려 든다
7. **`bucket.list(prefix, { limit: 1000 })`** — supabase-js `list()`의 기본 limit이
   **100**이라, 한 폴더에 100개가 넘으면 나머지가 조용히 안 지워진다.
   메인 에이전트 리뷰에서 잡은 결함이다. 번들 상한이 `MAX_FILES`(300)라 1000이면 넉넉하다

### 어드민 화면

8. **파일 개수는 이번 업로드에서만 보인다.** [01](01-요구사항.md) §2 A3은 "이미 올린
   번들의 **파일명과 개수**"였지만, 다시 연 화면에서 개수를 세려면 Storage를 재귀
   조회해야 한다. 표시 하나를 위해 폼을 열 때마다 왕복을 태울 이유가 없다고 봤다.
   **파일명은 언제나 보인다** — "뭐가 올라가 있는지 알아야 한다"는 A3의 목적은 그쪽이
   충족한다
9. **번들 교체는 "제거 → 다시 올리기" 2단계다.** `HtmlUpload`와 같은 패턴이라 화면
   문법을 맞췄다. 서버는 옛 경로를 폼이 아니라 **DB에서** 읽으므로, 이 2단계를 거쳐도
   옛 폴더 삭제는 정상 동작한다(폼의 `bundleIntent`가 최종적으로 `replace`가 된다)
10. **`upload()`에 `cacheControl: "31536000"`.** 폴더 키가 업로드마다 새 UUID라
    내용이 절대 바뀌지 않는다(D8) — 길게 캐시해도 안전하다
11. **`Blob` 생성 시 `new Uint8Array(...)`로 한 번 복사한다.** fflate가 돌려주는
    `Uint8Array<ArrayBufferLike>`가 `BlobPart`에 직접 대입되지 않는 TS 변성 문제다.
    파일 하나 최대 10MB라 복사 비용은 무시할 만하다

### 교차검증에서 나와 고친 것

12. **엔트리 이름의 `#` · `?` · `%` 를 거부한다** ([03](03-보안판단.md) §3-1에 반영).
    supabase-js는 업로드 경로를 **인코딩하지 않고** URL에 그대로 붙인다
    (`storage-js`의 `_getFinalPath`). `guide #2.png`는 `#` 뒤가 프래그먼트로 잘려
    **다른 키로 조용히 올라가고**, 위젯은 성공을 띄우는데 이미지만 404가 난다.
    HTML 안의 `<img src="guide #2.png">`도 같은 이유로 어차피 깨지므로 잃는 게 없다
13. **업로드 중에는 저장 버튼이 잠긴다** (`onBusyChange` → `canSave`).
    진행 중에 저장하면 `bundleIntent`가 아직 `keep`이라 컬럼은 안 붙고 이미 올라간
    파일 수십 개만 고아로 남는다. `ImageUpload`에도 같은 구멍이 있지만 이미지 한 장과
    파일 300개는 비용이 다르다([01](01-요구사항.md) §6이 스스로 그 구분을 한다)
14. **업로드 워커의 예외를 `try/catch`로 삼킨다.** 밖으로 새면 `Promise.all`이 즉시
    reject되고 **남은 워커가 뒤에서 계속 돌며** 에러 문구 아래로 진행 표시를 되살린다
15. **`detail_bundle_path`를 공통 상수가 아니라 상세 쿼리에만 붙인다.**
    [05](05-구현계획.md) §6은 `REGULAR_CLASS_PUBLIC_COLUMNS`에 넣으라고 했지만,
    목록은 그 값을 쓰지 않는다. 공통 상수에 넣으면 DDL 이전에 `/education` 목록까지
    같이 폴백으로 떨어진다. `detail_html`을 다루는 방식과 같게 맞췄다

### 기록만 하는 소이탈

16. 새 창 고지가 `aria-label`이 아니라 `<span class="sr-only">`다
    ([01](01-요구사항.md) §3). `selected-work.tsx`의 기존 패턴이고 기능은 동등하다
17. `planBundle`은 **경로 검증을 junk 필터보다 먼저** 돌린다. `__MACOSX/` 안의
    이상한 이름 하나 때문에 zip 전체가 거부될 수 있다 — 악의적 이름을 조용히
    넘기지 않는 쪽을 택했다
18. `index.html` 탐지는 대소문자를 구분한다. `Index.html`인 zip은 "index.html이
    없습니다"로 거부된다(메시지가 무엇을 고칠지 알려 준다)

> fflate API는 `context7`의 문서 조회 도구가 이 환경에 없어,
> 설치된 `node_modules/fflate/lib/index.d.ts`(0.8.3)를 직접 읽어 확인했다.

## 4. 배포 순서 — 코드를 DDL보다 먼저 내보내면 안 된다

컬럼이 없는 DB에서 이 코드가 돌면 **어드민이 먼저 깨지고, 공개 화면은 조용히
틀려진다.** 로컬이 곧 운영이므로 **지금 이 트리 상태가 그렇다.**

| 어디 | 증상 |
|---|---|
| 어드민 정규 클래스 **목록** | **500.** `REGULAR_CLASS_LIST_COLUMNS`가 `FIELDS`에서 자동 파생돼 없는 컬럼을 select하고, `SupabaseRepo.list()`는 에러를 그대로 던진다 |
| 어드민 **저장**(create/update) | 실패(`PGRST204`). `toRow`가 없는 컬럼을 보낸다 |
| 공개 `/education/programs/[slug]` | **조용히 정적 폴백.** 화면이 비지 않아 알아채기 어렵다 |
| 공개 목록(`/education`, `/education/programs`) | 영향 없음 — 위 §2 #15로 좁혀 뒀다 |

→ **DDL 적용 → 확인 쿼리 → 그 다음 배포.**
