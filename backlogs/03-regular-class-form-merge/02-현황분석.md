# 현황 분석

## 1. 두 파일의 실제 차이

### `new/page.tsx` (25줄)

```tsx

import { createRegularClass } from "../actions";

export default function NewRegularClassPage() {
  return (
    <div className="mx-auto flex max-w-2xl flex-col gap-6">
      <div>
        <Link href="/admin/content/education/regular-classes" className="…">
          <ArrowLeft className="size-4" aria-hidden />
          정규 클래스
        </Link>
        <h1 className="mt-3 text-2xl font-extrabold tracking-tight text-ink">
          정규 클래스 추가
        </h1>
      </div>
      <RegularClassForm onSave={createRegularClass} />

```

### `[id]/page.tsx` (35줄)

```tsx
export default async function EditRegularClassPage({ params }) {
  const { id } = await params;
  const item = await getContentData().education.regularClasses.get(id);
  if (!item) notFound();

  return (
    <div className="mx-auto flex max-w-2xl flex-col gap-6">
      {/* …위와 동일한 브레드크럼 + 제목 블록, 문구만 "수정"… */}
      <RegularClassForm initial={item} onSave={updateRegularClass.bind(null, id)} />
    </div>
  );
}
```

### 차이 정리

| | `new` | `[id]` |
|---|---|---|
| async | 아니오 | 예 (`params` await) |
| 데이터 조회 | 없음 | `.get(id)` + `notFound()` |
| 제목 | "정규 클래스 추가" | "정규 클래스 수정" |
| 폼 props | `onSave` | `initial` + `onSave` |
| **나머지** | **완전히 동일 (약 15줄)** | |

## 2. 중복의 실제 크기

**중복 = 브레드크럼 링크 + 제목 래퍼 마크업, 약 15줄.**

폼 필드 20여 개는 이미 `RegularClassForm` 하나에 있으므로 중복이 아니다.
백로그 01이 필드를 6개 더 추가해도 **이 두 파일은 안 바뀐다.**

→ 병합의 이득은 "필드 추가 시 두 곳을 고치는 문제 해결"이 아니다.
그 문제는 이미 없다. 이득은 **껍데기 15줄 제거 + 두 화면이 갈라질 여지 차단**이다.

## 3. 같은 패턴이 몇 벌 있나

> **정정 (2026-08-03)** — 아래 "11벌 / 22번"은 틀렸다. grep 전수 확인 결과
> `new` + `[id]` 쌍은 **12벌**이고, 여기에 `content/pillars/[id]`(추가가 없는
> 단독 화면)가 더 있어 같은 15줄이 **25번** 나온다. `content/pillars`를
> "목록형이라 제외"한 것이 오류였다 — `[id]` 화면은 같은 헤더를 갖고 있다.
> 25개 파일의 링크·h1 className은 **문자 단위로 완전히 일치**했다.

`(shell)/content/` 아래 `new` + `[id]` 쌍이 **12벌**이다.

```
education/club-cohorts, club-tiers, faqs, past-programs,
          regular-classes, reviews, stats
experts, inquiry-options, pillar-examples, stats, work
```
여기에 `content/pillars/[id]` 1개를 더해 **총 25개 페이지**.
(`education/org-training`은 목록 복귀 링크가 없어 실제로 제외 대상이 맞다)

즉 같은 15줄이 프로젝트에 **25번** 나온다. 정규 클래스만 고치면 나머지와
모양이 달라진다 — **"하나만 다른 구조"가 오히려 읽기 비용을 만든다.**

이게 D2(전체 적용 여부)가 중요한 이유다. 선택지는 셋이다.

1. 정규 클래스만 병합 → 11벌 중 1벌만 다른 모양
2. 공용 셸을 뽑아 11벌 전부 적용 → 일관되지만 범위가 커진다
3. 정규 클래스에서 **공용 셸을 만들어** 먼저 적용하고, 나머지는 손댈 일이
   생길 때 하나씩 옮긴다 → **권장**

## 4. Next.js App Router 제약

`/new`와 `/[id]`를 **물리적으로 한 파일**로 만들려면 `[id]/page.tsx` 하나만
남기고 `id === "new"`를 특수 취급해야 한다.

```tsx
const isNew = id === "new";
const item = isNew ? null : await getContentData()….get(id);
```

문제
- `new`가 예약어가 된다. 실제 행 id는 uuid라 지금은 충돌하지 않지만,
  **코드만 봐서는 그 사실을 알 수 없다** (uuid 규칙이 바뀌면 조용히 깨진다)
- 라우트가 하는 일이 파일 경로에서 안 읽힌다. `/new`가 어디서 처리되는지
  `[id]/page.tsx`를 열어야 안다
- 정적 세그먼트(`/new`)가 동적 세그먼트(`/[id]`)보다 **우선**하므로 `new/page.tsx`를
  지우지 않으면 아예 도달하지 않는다 — 지웠는지 여부가 동작을 좌우한다

얻는 것(15줄)에 비해 잃는 것이 크다. → [03-구현계획.md](03-구현계획.md)에서
이 방식(안 A)을 권장하지 않는 이유다.
