# 병합 범위 결정 — 이 작업의 기준 문서

## D1. 10쌍을 합치고 `inquiry-options`는 남긴다

**대칭 9쌍 + `past-programs` = 10쌍.**

왜 전부가 아닌가 — `inquiry-options`는 두 화면이 실제로 다르다(02 §3). 합치면
셸 prop 네 개가 전부 삼항이 되고, 줄어드는 줄보다 늘어나는 분기가 많다.

왜 일부만인데 괜찮은가 — 결정기록 03의 D2는 *"일부만 바꾸면 공통 패턴이 두 개가
되어 다음 사람이 어느 쪽이 기준인지 다시 판단해야 한다"*는 이유로 25개 전체 적용을
택했다. **그 논리가 여기서도 성립한다** — 다만 결과가 반대다. 지금은 "정규 클래스만
합쳐진 예외 1개"라 패턴이 이미 둘이다. 10쌍을 합치면 **`[id]` 한 파일이 기준,
`inquiry-options` 하나가 명시적 예외**가 되어 예외가 1개로 유지되고, 그 예외는
"구조가 다르다"는 **파일을 열면 보이는 이유**를 갖는다.

### 왜 지금 뒤집나 — 근거는 하나뿐이다

결정기록 03이 치른다고 본 값 셋 중 **②(정적 프리렌더 손실)가 사실이 아니다**
(02 §4). 어드민은 이미 전부 동적이고, 실인증 배선 후에도 그렇다.

①(예약 id)과 ③(경로 가독성)은 그대로 치른다. 그 값을 치르고 얻는 것은
**파일 10개 · 약 85줄 · "패턴이 둘"인 상태의 해소**다.

> 03의 판단이 그때 틀렸다는 뜻이 아니다. 근거 하나가 검증되지 않은 채였고,
> 지금 재면 성립하지 않는다. 이건 결정기록 05의 D4와 같은 종류의 정정이다.

### 버린 대안

| 안 | 내용 | 왜 버렸나 |
|---|---|---|
| **A** | 11쌍 전부 합친다 | `inquiry-options`가 삼항 덩어리가 된다 |
| **B** | 아무것도 안 한다 (03 유지) | 근거 ②가 무효라 유지할 이유가 하나 줄었다. "패턴이 둘"인 상태도 그대로 남는다 |
| **C** | 반대로 정규 클래스를 되돌려 두 파일로 만든다 | 일관성은 얻지만 근거 ②가 무효인 지금, 파일 수가 늘어나는 방향이다 |
| **D** | 병렬 라우트·인터셉트 라우트 | 이 규모에 과하다. Next 기능 하나를 더 배워야 읽힌다 |

**안 C는 진지하게 검토했다.** "일관성"만 보면 되돌리기도 답이다. 병합 쪽을 택한
이유는 두 가지 — (1) 근거 ②가 사라져 병합의 비용이 실제로 줄었다, (2) 되돌리면
정규 클래스 `[id]`에 적힌 20줄 주석과 결정기록 03의 판단 근거가 통째로 폐기된다.

## D2. URL은 바꾸지 않는다

`/new` 경로 유지. 목록 페이지 13곳이 하드코딩하고 있고(02 §5), 이 작업의 diff를
라우트 껍데기 안에 가둔다. 결정기록 03의 D3과 같은 판단이다.

## D3. `new/page.tsx`는 반드시 지운다

Next App Router는 **정적 세그먼트가 동적 세그먼트보다 우선**한다. `new/page.tsx`를
남겨 두면 `[id]`의 `isNew` 분기에 **도달조차 하지 않는다.** 지웠는지 여부가 동작을
좌우하므로, 검증 체크리스트에 `new/` 디렉터리 부재 확인을 넣는다(05 §1).

## D4. `new` 예약 id 제약은 셸 문서 한 곳에 적는다

정규 클래스 `[id]/page.tsx`에는 이 제약을 설명하는 **20줄짜리 주석**이 있다.
그걸 10개 파일에 복사하지 않는다 — 같은 문단이 11벌 있으면 고칠 때 11곳이 된다.

| 어디 | 무엇을 |
|---|---|
| `docs/06-admin/06-콘텐츠-폼-공용셸.md` §3 | 제약의 **본문**. `new`가 예약 id인 이유, id 생성 방식을 바꿀 때 볼 것 |
| 각 `[id]/page.tsx` | **1~2줄 포인터**만 — `/** 추가·수정 겸용. 제약은 docs/06-admin/06 §3. */` |
| `education/regular-classes/[id]/page.tsx` | 기존 20줄 주석을 **포인터로 줄인다.** 더는 예외가 아니므로 "합치기 전에는 정적이었다" 같은 문장도 폐기 |

## D5. 커밋은 3덩이로 쪼갠다

| # | 범위 | 왜 |
|---|---|---|
| 1 | 비교육 4쌍 (`work` `experts` `stats` `pillar-examples`) | 가장 단순. 여기서 패턴이 굳는다 |
| 2 | 교육 5쌍 (`club-cohorts` `club-tiers` `faqs` `reviews` `stats`) | 1과 동일 기계 작업 |
| 3 | `past-programs` + 문서·주석 4곳 | 유일하게 판단이 필요한 코드 + 문서 뒤집기 |

한 커밋에 몰면 회귀가 났을 때 어느 컬렉션인지 bisect가 안 된다. 결정기록 03도
같은 이유로 컬렉션별로 쪼갰다.

**문서 수정을 3번에 붙이는 이유** — 코드가 다 들어간 뒤라야 문서가 거짓말을 하지
않는다. 1·2번 커밋 시점에는 문서의 "합치지 않았다"가 아직 부분적으로 참이다.
