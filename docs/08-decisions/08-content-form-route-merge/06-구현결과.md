## 2. 계획과 달랐던 것

### 2-1. `experts`의 변수명 — 리뷰에서 잡아 고쳤다

서브에이전트가 기존 파일의 `const expert`를 그대로 살렸다. 동작에는 문제가 없지만
나머지 9개가 `item`이라 **패턴을 하나로 만드는 것이 이 작업의 목적**이라 맞췄다.
고치다가 JSX 쪽 `initial={expert}`를 빠뜨렸고 `tsc`가 잡았다.

→ 이 한 건이 "타입 검사만으로 충분한 구간"과 "눈으로 봐야 하는 구간"의 경계를
보여 준다. 이름 통일은 tsc가 잡아 주지만, **어느 이름으로 통일할지는 안 잡아 준다.**

### 2-2. `past-programs`는 `getContentData()`를 `isNew`에도 부른다

```tsx
const data = getContentData();   // isNew여도 호출된다
```

요구사항 R3의 문구는 "`isNew`면 `getContentData()`를 아예 부르지 않는다"였지만,
이 함수는 **리포지터리 객체를 고르는 팩토리**이고 쿼리를 내지 않는다
(`content-data.ts:248` — env를 보고 Supabase 리포지터리 또는 mock을 돌려준다).
실제 조회(`.get()`·`.listByProgram()`)는 둘 다 `isNew` 분기 안에 있다.

→ R3의 의도(존재하지 않는 행을 매번 찾지 않는다)는 지켜졌다. 문구가 팩토리와
쿼리를 구분하지 않았던 것이라 그대로 뒀다.

## 3. 검증에서 나온 것 — 계획에 없던 발견

### 3-1. uuid 형식이 아닌 id는 404가 아니라 **500**이다

```
/admin/content/work/00000000-0000-0000-0000-000000000000  → 404  ✅ notFound()
/admin/content/work/abc                                   → 500  ⚠️
```

Postgres가 `invalid input syntax for type uuid`로 거절하고, 그 에러가 `notFound()`
앞에서 던져진다. **기존 동작이다** — 병합 전에도 `[id]`는 모든 id를 그대로
조회로 넘겼다. 이 작업은 오히려 `"new"` 하나를 조회 앞에서 걸러 냈다.

→ 고치지 않았다. 이 작업의 범위가 아니고, 어드민 내부 화면이라 사용자가 임의
문자열을 타이핑해 닿는 경로가 아니다. 다만 **다음에 이 부근을 만질 때 후보다.**

### 3-2. 덤 — `new`가 예약 id인 제약이 생각보다 안전하다

3-1의 부산물이다. Supabase 모드에서 `id`는 uuid 컬럼이라 **`"new"`는 애초에 행
id가 될 수 없다.** 타입 시스템이 아니라 DB 스키마가 막는다. 03-결정 D1이 치르기로
한 값 ①은 mock 모드(`work_1` 꼴)에서만 이론적으로 남는다.

### 3-3. 저장 경로는 검증하지 않았다 — **의도적이다**

로컬과 배포가 **DB를 공유한다**(`docs/07-dev/02-개발상태.md` §먼저 알아야 할 것).
추가 화면에서 저장하면 그 즉시 www.kpopsoft.com에 새 행이 보인다. 그래서
체크리스트 §3의 "추가 화면에서 저장 → 목록에 새 행" 항목은 **돌리지 않았다.**

대신 확인한 것 — 4개 컬렉션(`work`·`faqs`·`past-programs`·`regular-classes`)에서
추가 화면 200 + 제목 "… 추가" + 빈 폼, 수정 화면 200 + 제목 "… 수정" + 채워진 폼
(13·2·12·20개 필드), 없는 uuid 404, 추가 화면에 삭제 버튼 없음, `min-h-11` 생존,
`past-programs` 갤러리가 추가엔 없고 수정엔 있음.

**폼이 열리는 것과 저장되는 것은 다르다.** 저장 경로는 `onSave` prop이 바뀐 것이
전부이고 액션 함수 자체는 무수정이지만, 그래도 이 항목은 **닫히지 않았다.**
다음에 어드민을 만질 때 스테이징이 생기면 그때 닫는다.
