### 2-2. `past-programs`는 `getContentData()`를 `isNew`에도 부른다

```tsx
const data = getContentData();   // isNew여도 호출된다
```

요구사항 R3의 문구는 "`isNew`면 `getContentData()`를 아예 부르지 않는다"였지만,

실제 조회(`.get()`·`.listByProgram()`)는 둘 다 `isNew` 분기 안에 있다.

→ R3의 의도(존재하지 않는 행을 매번 찾지 않는다)는 지켜졌다. 문구가 팩토리와
쿼리를 구분하지 않았던 것이라 그대로 뒀다.

## 3. 검증에서 나온 것 — 계획에 없던 발견

### 3-1. uuid 형식이 아닌 id는 404가 아니라 **500**이다

```
/admin/content/work/00000000-0000-0000-0000-000000000000  → 404  ✅ notFound()
/admin/content/work/abc                                   → 500  ⚠️
```

Postgres가 `invalid input syntax for type uuid`로 거절하고, 그 에러가 `notFound()`
앞에서 던져진다. **기존 동작이다** — 병합 전에도 `[id]`는 모든 id를 그대로
조회로 넘겼다. 이 작업은 오히려 `"new"` 하나를 조회 앞에서 걸러 냈다.

→ 고치지 않았다. 이 작업의 범위가 아니고, 어드민 내부 화면이라 사용자가 임의
문자열을 타이핑해 닿는 경로가 아니다. 다만 **다음에 이 부근을 만질 때 후보다.**

덤으로 이게 R3의 **런타임 증거**가 된다. Supabase 모드에서 `abc`는 500인데
`new`는 200이다. `isNew`가 조회를 안 걸렀다면 `new`도 같은 uuid 거절에 걸렸을
것이다. 코드를 읽지 않고도 "추가 화면은 조회하지 않는다"가 확인된다.

### 3-2. 덤 — `new`가 예약 id인 제약이 생각보다 안전하다

3-1의 부산물이다. Supabase 모드에서 `id`는 uuid 컬럼이라 **`"new"`는 애초에 행
id가 될 수 없다.** 타입 시스템이 아니라 DB 스키마가 막는다. 03-결정 D1이 치르기로
한 값 ①은 mock 모드(`work_1` 꼴)에서만 이론적으로 남는다.

### 3-3. 저장 경로 — 08-06에는 못 닫았고, **2026-08-09에 닫았다**

08-06에 돌리지 않은 이유는 하나였다. 로컬과 배포가 **DB를 공유해서**
(`docs/07-dev/02-개발상태.md` §먼저 알아야 할 것) 추가 화면에서 저장하면 그 즉시
www.kpopsoft.com에 새 행이 생긴다. 그래서 그날은 화면이 **열리는 것**까지만 봤다.

**목 모드로 돌려서 닫았다.** `getContentData()`는 `NEXT_PUBLIC_SUPABASE_URL`과
`SUPABASE_SERVICE_ROLE_KEY`가 **둘 다** 있을 때만 Supabase를 본다
(`content-data.ts:248`). 서비스 키 하나만 비우면 인메모리 목 리포로 떨어진다.
방법은 [`../../07-dev/02-개발상태.md`](../../07-dev/02-개발상태.md) §목 모드로 저장 검증하기.

결과 — **병합한 라우트 11개 전부**에서 추가·수정이 실제로 저장된다
(10쌍 + 이미 병합돼 있던 `regular-classes`).

| | |
|---|---|
| 추가 저장 → 목록에 새 행 | 11/11 |
| 수정 저장 → 값이 실제로 바뀐다 | 11/11 |
| 제목이 "… 추가" / "… 수정"으로 갈린다 | 11/11 |
| 수정 화면이 기존 값으로 채워진다 | 11/11 |

체크리스트 §3은 **최소 4개**를 요구했지만, 자동화해 두니 나머지 7개를 더 도는
비용이 거의 없었다. `onSave` 삼항이 11곳에 복사된 작업이라 표본보다 전수가 맞다.

**갤러리(§4)도 같이 닫혔다.** 추가 화면에는 갤러리 블록이 없고, 저장한 뒤 그 행을
열면 나타난다. 이미지 추가 → 1장(배지 "총 2장"), 휴지통 → 0장, **새로고침 후에도
0장**. 인라인 `"use server"` 클로저가 `programId`를 물고 살아 있다는 뜻이다.

> Storage 업로드는 브라우저에서 가로챘다 — Storage도 로컬·운영이 한 프로젝트라
> 그냥 올리면 운영 버킷에 객체가 생긴다. 실제로 나간 요청은 없다.

**목 모드로는 못 닫는 것 하나** — 체크리스트 §5의 *"이름만 고쳐 저장해도 업로드
자료가 남는다"*. 목 리포는 동반 테이블을 아예 모델링하지 않아
(`MockRegularClassRepo.upsertHtmlSource`가 no-op) 이 회귀가 성립할 무대가 없다.
**이 항목은 실제 DB에서 이미 따로 닫혀 있다** —
[`../../06-admin/07-과정-상세본문-HTML과-번들.md`](../../06-admin/07-과정-상세본문-HTML과-번들.md) §3-3.
