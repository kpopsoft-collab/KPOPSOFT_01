# 요구사항

## R1. 한 컬렉션의 추가·수정은 한 파일이 담당한다

`[id]/page.tsx` 하나가 `id === "new"`로 두 화면을 겸한다. `new/` 세그먼트는 없앤다.

```tsx
const isNew = id === "new";
const item = (isNew ? undefined : await …get(id)) ?? undefined;
if (!isNew && !item) notFound();
```

정규 클래스가 이미 이 모양이다. **새로 발명하는 패턴이 아니라, 하나뿐이던 예외를
기준으로 올리는 것**이다.

## R2. URL은 바뀌지 않는다

`/admin/content/work/new`, `/admin/content/work/<id>` 둘 다 지금 그대로 200이어야
한다. 목록 페이지 13곳이 두 경로를 하드코딩하고 있고(`href="…/new"`,
`<EditLink href={`…/${item.id}`} />`), 그 파일들은 이 작업에서 손대지 않는다.

## R3. 추가 화면은 조회를 하지 않는다

`isNew`일 때 `getContentData()`를 **아예 부르지 않는다.** 존재하지 않는 행을 매번
찾는 낭비를 막는 규칙이고, 병합 후에는 파일 경로가 아니라 이 코드로만 확인된다.

> 기존 확인법이었던 "빌드 출력에서 `/new`가 ○, `/[id]`가 ƒ"는 **지금도 이미 성립
> 하지 않는다** — 어드민 페이지는 전부 동적이다. 02 §4를 본다.

## R4. 추가 화면에 삭제·부속 관리 UI가 새지 않는다

- 삭제 버튼은 지금도 폼 화면에 없다(목록의 `DeleteButton`이 담당). 유지한다.
- `past-programs`의 `GalleryManager`, 그 밖에 **부모 행이 있어야 성립하는 블록**은
  `!isNew`로 감싼다. 갤러리는 `programId`를 FK로 쓰므로 추가 화면에 뜨면 안 된다.

## R5. 폼 컴포넌트는 건드리지 않는다

`RegularClassForm` 계열 13개 폼과 `ContentFormShell`의 **props·마크업은 무수정**이다.
이 작업이 고치는 것은 라우트 껍데기뿐이다. 폼에 필드를 더하는 다른 작업과 편집
교집합이 0이어야 한다.

## R6. 문서와 코드 주석이 코드와 같은 말을 한다

병합 후에도 `docs/06-admin/06-콘텐츠-폼-공용셸.md` §3이 "합치지 않았다"라고 적혀
있으면 **문서가 우선**이라 다음 사람이 되돌린다. 코드 커밋과 문서 커밋을 같은
작업 안에서 끝낸다.

## 하지 않는 것

| | 왜 |
|---|---|
| `inquiry-options` 병합 | 두 화면이 실제로 다르다. 합치면 거의 모든 prop이 삼항이 된다 (02 §3) |
| `pillars`에 추가 화면 신설 | 이 작업의 범위가 아니다. 핵심 비즈니스 카드는 고정 3장이라 지금 추가가 없는 것이 맞다 |
| `FormActions` 승격 | 06-admin/06 §5의 "알려진 중복"은 별건이다. 섞으면 diff가 커진다 |
| `actions.ts` 경로 상수 추출 | 결정기록 03에서 이미 폐기됐다 (`"use server"` export 제약) |
| URL 변경 (`/new` → 쿼리스트링 등) | R2 |
