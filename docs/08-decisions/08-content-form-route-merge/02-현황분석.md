# 현황 분석 — 2026-08-06 실측

## 1. 남은 쌍은 11벌이다

`src/app/admin/(shell)/content/` 아래 `new` + `[id]` 쌍 **11벌**.
12번째였던 `education/regular-classes`는 **2026-08-04에 이미 병합**됐다.

| 등급 | 대상 | 수 |
|---|---|---|
| **A. 대칭** | `work` `experts` `stats` `pillar-examples` / `education/`의 `club-cohorts` `club-tiers` `faqs` `reviews` `stats` | 9쌍 |
| **B. 조건부 블록 1개** | `education/past-programs` | 1쌍 |
| **C. 구조가 다름** | `inquiry-options` | 1쌍 |

대상 아님 — `pillars`(`[id]`만, 추가 화면 없음), `education/org-training`(싱글턴).

## 2. A급 9쌍의 실제 차이

두 파일이 다른 지점은 **네 곳뿐**이고, 9쌍이 전부 같은 모양이다.

| | `new` | `[id]` |
|---|---|---|
| async | 아니오 | 예 (`params` await) |
| 데이터 조회 | 없음 | `.get(id)` + `notFound()` |
| 제목 | `"… 추가"` | `"… 수정"` |
| 폼 props | `onSave` | `initial` + `onSave` |
| **나머지** | **완전히 동일** | |

줄 수 (`wc -l`)

```
new    11줄 × 3 (work, experts, stats)  +  15줄 × 6  = 123줄
[id]   22줄 × 3                          +  26줄 × 6  = 222줄
```

병합하면 **`new` 123줄이 사라지고 `[id]`에 `isNew` 분기가 쌍당 4~5줄 붙는다.**
→ 파일 9개 삭제, **순감 약 78줄.**

`past-programs`까지 넣으면 파일 10개, **순감 약 85줄.**

## 3. B·C급이 다른 이유

### B. `past-programs` — 합칠 수 있다

`[id]`에만 `GalleryManager`가 붙어 있고, 파일 안에 이미 이유가 적혀 있다.

```tsx
{/* 갤러리는 부모 행이 있어야 붙일 수 있어 추가 화면에는 없고 수정 화면에만 있다. */}
<GalleryManager programId={id} images={images} … />
```

`{!isNew && <GalleryManager … />}` 한 겹이면 된다. 이미지 조회
(`pastProgramImages.listByProgram(id)`)도 같은 분기 안으로 넣어 **추가 화면에서
쿼리가 안 나가게** 한다(R3).

### C. `inquiry-options` — 합치면 손해다

| | `new` (20줄) | `[id]` (44줄) |
|---|---|---|
| `title` | `"유형 추가"` 고정 | **행 값** `type.label` |
| `description` | 있음 (프로젝트 통틀어 유일) | 없음 |
| `className` | `"max-w-xl"` | `"gap-8"` |
| 본문 | `TypeForm` 하나 | `<section>` 2개 — `TypeForm`(`showActive`) + `SubtypeManager` |
| `onSave` | 인라인 서버액션 래퍼 | `updateType.bind(null, id)` |

**여섯 항목이 전부 다르다.** 합치면 셸 prop 네 개가 모두 삼항이 되고 본문도
분기가 갈린다. 지금 두 파일이 각자 읽히는 편이 낫다 → 제외(D1).

## 4. ⚠️ 옛 반대 근거 3개 재검증 — 하나가 무효다

원본은 [`docs/08-decisions/03-…/02-현황분석.md`](../03-regular-class-form-merge/02-현황분석.md) §4.

### ① "`new`가 예약 id가 된다" → **여전히 유효**

`[id]`에 들어오는 값은 슬러그가 아니라 행 id다 — mock은 `work_1`·`expert_1` 꼴
(`src/lib/admin/mock-content.ts`), Supabase는 uuid PK(`supabase-content.ts`의
`.eq("id", id)`). 실제 충돌은 없다. 다만 **코드만 봐서는 안 보이는 암묵 제약**이라는
지적은 그대로다 → D4에서 어디에 적을지 정한다.

### ② "`/new`가 정적 프리렌더에서 빠진다" → **지금 사실이 아니다**

최신 빌드 산출물(`.next`, 2026-08-05 23:40)을 실측했다.

```
$ find .next/server/app/admin -name "*.html"
.next/server/app/admin/login.html          ← 이것 하나뿐

$ prerender-manifest.json 의 /admin 경로
/admin/login
```

**`(shell)` 아래는 `/new`를 포함해 이미 전부 동적이다.** 셸 레이아웃이
`requireAdmin()`을 거치고(`src/app/admin/(shell)/layout.tsx:19`), 실인증을 배선하면
`createSupabaseServerClient()`가 `cookies()`를 읽으므로(`src/lib/supabase/server.ts:14`)
**앞으로도 정적이 될 일이 없다.**

→ 병합해도 **잃는 정적성이 0**이다. 결정기록 03이 치른다고 본 값 하나가 사라졌다.

→ 덤으로, [`docs/06-admin/06-콘텐츠-폼-공용셸.md`](../../06-admin/06-콘텐츠-폼-공용셸.md)
§4의 확인법("빌드 출력에서 `/new`가 ○, `/[id]`가 ƒ로 갈리는지")도 **현재 성립하지
않는다** — 전부 ƒ다. 병합과 무관하게 이 문장은 고쳐야 한다.

### ③ "라우트가 하는 일이 파일 경로에서 안 읽힌다" → **유효. 유일한 실제 쟁점**

취향이 아니라 탐색 비용 문제다. `/new`가 어디서 처리되는지 알려면 `[id]/page.tsx`를
열어야 한다. 다만 **지금은 그 비용을 이미 절반 치르고 있다** — 정규 클래스 하나만
다른 모양이라, 어느 쪽이 기준인지 매번 확인해야 한다.

## 5. 목록 페이지가 거는 링크 — 안 바뀐다

13개 목록 페이지가 두 경로를 하드코딩한다.

```tsx
<Link href="/admin/content/work/new">…</Link>
<EditLink href={`/admin/content/work/${item.id}`} />
```

URL을 유지하므로(R2) **이 13개 파일은 무수정**이다.
