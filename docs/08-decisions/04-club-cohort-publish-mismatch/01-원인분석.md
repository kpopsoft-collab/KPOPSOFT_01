# 원인 분석

## 1. 어긋나는 지점

앱은 `ContentBase`를 통해 **모든** 콘텐츠 타입에 `isPublished`를 강제한다.

```ts
// src/lib/admin/content-types.ts:14
export type ContentBase = {
  id: string;
  sortOrder: number;
  /** Hidden from the public site when false. */
  isPublished: boolean;
};
```

`EducationClubCohort`도 `ContentBase &`로 정의돼 있어 이 필드를 갖는다.
그리고 매핑 테이블이 그것을 컬럼으로 번역한다.

```ts
// src/lib/admin/supabase-content.ts:37
const COMMON: FieldMap = [
  ["sortOrder", "sort_order"],
  ["isPublished", "is_published"],   // ← 모든 테이블에 붙는다
];

// :118
education_club_cohorts: [ ...COMMON, ["label","label"], ... ],
```

그런데 테이블에는 그 컬럼이 없다.

```sql
-- supabase/migrations/20260802120000_p3_education_ver3.sql:82
create table if not exists public.education_club_cohorts (
  id, label, status, recruit_period, run_period, price, list_price,
  capacity, note, cta_disabled, show_price, show_capacity,
  show_schedule, show_cta, sort_order, created_at, updated_at
  -- is_published 없음
);
```

**이건 실수가 아니라 의도였다.** 같은 파일 `:299`의 RLS 블록이 기수를
"is_published이 없는 테이블" 그룹에 넣으면서 이유를 적어 뒀다.

> 기수는 목록 자체가 안내물이라 숨길 행이 없고(감출 기수는 `status='ended'`),
> 갤러리는 부모 프로그램의 공개 여부를 따라간다.

즉 **스키마 쪽 판단이 맞고, 앱 타입이 그 판단을 따라가지 않은 것**이다.

## 2. 왜 읽기는 멀쩡한가

`fromRow()`가 없는 컬럼을 건너뛰기 때문이다.

```ts
// supabase-content.ts:186
for (const [camel, snake] of FIELDS[table]) {
  const v = row[snake];
  if (v === null || v === undefined) continue;   // ← is_published가 여기서 사라진다
  out[camel] = v;
}
```

`item.isPublished`가 `undefined`로 오고, 목록의 `PublishToggle`이 그 값을 받는다
(`club-cohorts/page.tsx:49`). 타입은 `boolean`인데 런타임 값은 `undefined`다 —
타입이 거짓말을 하고 있고, 화면은 falsy라 "비공개"처럼 보인다.

반대로 `toRow()`는 값이 `undefined`가 **아닐 때만** 싣는다.

```ts
// supabase-content.ts:197
if (obj[camel] !== undefined) out[snake] = obj[camel];
```

폼은 항상 `boolean`을 보내므로(`cohort-form.tsx:65`) 쓰기에서는 **반드시** 실린다.
그래서 **읽기는 통과, 쓰기는 실패**라는 비대칭이 생긴다.

## 3. 쓰기가 일어나는 경로 세 곳

| 경로 | 파일 |
|------|------|
| 추가 | `cohort-form.tsx:65` → `actions.ts` `createCohort` |
| 수정 | `cohort-form.tsx:65` → `actions.ts` `updateCohort` |
| 공개 토글 | `club-cohorts/page.tsx:50` → `actions.ts:37` `setCohortPublished` |

`setCohortPublished`는 `update(id, { isPublished: next })`로 **그 필드 하나만**
보낸다. 즉 이 액션은 100% 실패한다.

## 4. 다른 테이블은 괜찮은가 — 전수 확인함

`COMMON`을 쓰는 12개 테이블의 `CREATE TABLE` 본문과 `ALTER TABLE ... ADD COLUMN`을
전부 파싱해 대조했다.

```
work_items, experts, stats, home_pillars, home_pillar_examples,
education_regular_classes, education_club_tiers, education_past_programs,
education_reviews, education_faqs, education_stats        → is_published 있음
education_club_cohorts                                     → 없음  ◀ 유일
```

`education_org_training`(싱글턴)과 `education_past_program_images`(갤러리)는
`COMMON`을 안 쓰는 별도 리포지토리라 해당 없다.

→ **어긋난 테이블은 기수 하나뿐이다.**

## 5. 시드 스크립트는 왜 안 깨지나 — 안 A의 결정적 근거

`scripts/seed-education-ver3.cjs`는 `FIELDS` 매핑을 **안 탄다.** supabase-js로
컬럼을 직접 적어 넣는데, 거기에 `is_published`가 없다.

```js
// scripts/seed-education-ver3.cjs:89
education_club_cohorts: C.clubCohorts.map((c, i) => ({
  label, status, recruit_period, run_period, price, list_price,
  capacity, note, cta_disabled, show_price, show_capacity,
  show_schedule, show_cta, sort_order,          // ← is_published 없음
})),
```

같은 파일에서 `education_regular_classes`·`education_club_tiers` 등 다른
테이블은 `is_published`를 넣는다. **기수만 의도적으로 뺐다.**

→ 스키마(§1의 RLS 주석), 시드, 공개 리더 셋이 모두 "기수에는 공개 축이 없다"로
일관돼 있고, **어드민 타입 하나만 어긋나 있다.** 고칠 쪽은 어드민이다.

## 6. 공개 화면은 이 버그와 무관하다

`getPublicClubCohorts()`(`public-content.ts:333`)는 `read()`로 읽고, 어드민
경로를 타지 않는다. 그리고 기수는 **전부 노출되는 것이 아니다** —
모달은 `getActiveCohort()`로 `open → closed → upcoming` 중 **하나**를 고르고
(`education-content.ts:567`), `getUpcomingCohorts()`가 `ended`와 현재 기수를
제외한 나머지를 붙인다(`:581`).

또 `read()`는 **정상 0행이면 정적 폴백을 반환한다**(`public-content.ts:276`).
따라서 테이블이 비어 있으면 공개 화면은 `education-content.ts:522`의 정적 4행을
보여준다. 이건 결정기록 01이 정규 클래스에서 지적한 것과 **같은 뿌리의 문제**다
([01/06 §P1-5](../01-regular-class-schedule-and-html/06-교차검증-결과.md)).
이 결정기록에서는 고치지 않는다 — 범위가 다르다.

→ 검증할 때 이 사실을 모르면 **정상 동작을 회귀로 오독한다**
([02 §3](02-수정계획.md) 주의).

## 7. 왜 지금까지 안 드러났나

- 목 모드(`NEXT_PUBLIC_SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` 미설정)에서는
  `MockRepo`가 메모리 배열을 쓰므로 **정상 동작한다**(`content-data.ts:199`).
- 실제 DB 모드에서도 **읽기·공개 화면은 멀쩡**하다(§2).
- 기수는 자주 고치는 데이터가 아니다.
