# 요구사항

## 1. 원문 요청

> `.../regular-classes/new`
> - `.../regular-classes/[id]` 페이지랑 병합해서 사용할 예정

## 2. 해석

두 화면이 사실상 같은 폼이므로 **한 벌로 관리한다**는 뜻으로 읽는다.
필드가 늘 때(예: 결정기록 01의 일정·HTML) 두 곳을 각각 손대지 않게 하는 것이
목적이다.

**이미 절반은 그렇게 돼 있다.** 필드는 `RegularClassForm` 한 컴포넌트에 있고,
페이지 파일 두 개는 제목과 `onSave`만 다르다. 그래서 이 작업의 실질 범위는:

- 남아 있는 껍데기 중복(브레드크럼 링크 + 제목 블록, 약 15줄 × 2)을 없앤다
- 추가/수정에서 화면이 갈라질 여지를 구조적으로 막는다

## 3. 요구사항

### R1. 화면은 하나의 정의에서 나온다
추가와 수정이 같은 컴포넌트 한 벌에서 렌더된다. 어느 한쪽에만 필드가 붙는 일이
구조적으로 불가능해야 한다.

### R2. URL은 유지한다
- `/admin/content/education/regular-classes/new`
- `/admin/content/education/regular-classes/[id]`

두 경로 모두 그대로 동작한다. 목록 페이지의 `추가` 버튼과 `EditLink`가 이미
이 경로를 가리키고, 어드민 북마크도 있을 수 있다.

### R3. 모드별로 달라야 하는 것은 유지한다

| | 추가 | 수정 |
|---|---|---|
| 제목 | 정규 클래스 추가 | 정규 클래스 수정 |
| 저장 동작 | `createRegularClass` | `updateRegularClass.bind(null, id)` |
| 초기값 | 없음(기본값) | DB 행 |
| 없는 id | — | `notFound()` |
| 삭제 버튼 | 없음 | (선택) 있으면 유용 |

**추가 화면에 삭제 버튼이 나오면 안 된다.** 병합에서 가장 흔한 사고다.

### R4. 데이터 로딩은 수정에서만
추가 화면이 `getContentData().…get()`을 호출하지 않는다. 병합을 잘못하면
추가 화면이 매번 존재하지 않는 행을 조회한다.

### R5. 폼 컴포넌트의 계약은 그대로
`RegularClassForm`의 `initial?` / `onSave` 시그니처를 바꾸지 않는다.
결정기록 01이 같은 파일을 고치므로, 여기서 시그니처까지 바꾸면 충돌 지점이 겹친다.

## 4. 하지 않을 것

- **폼 필드 변경** — 결정기록 01의 범위다
- **다른 교육 폼 6종에 동시 적용** — 정규 클래스에서 검증 후 별건(D2)
- **URL 구조 변경** — `?mode=new` 같은 쿼리 방식으로 바꾸지 않는다(R2)
- **`(shell)` 레이아웃·`FormActions` 수정** — 교육 폼 7종이 공유한다

## 5. 받아들임 기준

- [ ] 두 URL 모두 기존과 동일하게 동작한다
- [ ] 제목이 모드에 맞게 나온다
- [ ] 추가 → 저장 → 목록에 새 행이 생긴다
- [ ] 수정 → 저장 → 값이 바뀐다
- [ ] 없는 id → 404
- [ ] 추가 화면에서 DB 조회가 일어나지 않는다
- [ ] 추가 화면에 삭제 버튼이 없다
- [ ] 브레드크럼·제목 마크업이 **한 곳에만** 있다
- [ ] 다른 교육 폼 6종이 영향받지 않았다
