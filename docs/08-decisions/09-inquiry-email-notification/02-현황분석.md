# 02 — 현황분석

조사일 2026-08-11. 값은 전부 실측이다.

## 1. 문의는 저장되고 있다 — 유실 없음

운영 Supabase `inquiries` 테이블을 service_role로 직접 조회했다.

```
총 3건
2026-08-10T14:46:17Z  소프트웨어 개발  contact="kyk***@gmail.com / 010-2338-****"
2026-08-02T11:50:34Z  소프트웨어 개발  contact="kyk***@gmail.com / 010-2338-****"
2026-07-09T13:33:30Z  프로젝트 문의    contact=""            (최초 스모크 테스트)
```

앞의 두 건은 `- 예상 일정:` / `- 예상 예산:` 블록을 달고 있다.
`composeMessage()`가 붙이는 형식이라(`src/lib/inquiry-actions.ts:47-60`)
**현재 폼을 타고 들어온 진짜 제출**이 맞다.

맨 위 건은 WP 258 신고(14:48:21)보다 **2분 앞선다.** 같은 건이다.

→ **"메일이 안 온다"는 곧 "문의를 못 받았다"가 아니다.** 3건 다 어드민에 있다.

`src/lib/email.ts:60-72`

```ts
const apiKey = process.env.RESEND_API_KEY;
if (!apiKey) {
```

그래서 서버 어디에도 "메일 못 보냈다"는 신호가 안 남는다.

## 3. env 실측

`.env.local`(로컬):

| 키 | 상태 |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` / `ANON_KEY` / `SERVICE_ROLE_KEY` | 채워짐 |
| `RESEND_API_KEY` | **비어 있음** ← 직접 원인 |
| `RESEND_FROM` | **비어 있음** |
| `INQUIRY_NOTIFY_TO` | **비어 있음** |
| `SUPABASE_ACCESS_TOKEN` | 비어 있음 (MCP 전용, 앱과 무관) |

**Vercel 운영 env는 이 저장소에서 확인할 수 없다**(`.vercel/` 없음, link 안 됨).
정황상 운영도 비어 있다고 본다 — `docs/06-admin/05-구축-실행계획.md:63`이
"Resend 실발송"을 미완 체크리스트로 남겨 뒀고 이후 처리 기록이 없다.
→ 그래도 **첫 단계에서 눈으로 확인한다**([04](04-구현계획.md) 0단계).

## 4. 수신자 조회는 정상

`resolveRecipients()`(`email.ts:29-44`)는 `INQUIRY_NOTIFY_TO`가 비면
`admin_users`로 폴백한다. 실측:

```
admin_users — 1행
  user_id 56b06fba-…  email kpopsoft@gmail.com
```

→ 승인 설계가 지정한 수신 주소와 **같다.** 이쪽은 막힌 데가 없다.

## 5. DNS 실측 — 이미 Cloudflare다 (결정적)

`kpopsoft.com`을 8.8.8.8로 조회한 결과다.

```
NS   nora.ns.cloudflare.com / houston.ns.cloudflare.com
MX   4  route1.mx.cloudflare.net
     57 route3.mx.cloudflare.net
     58 route2.mx.cloudflare.net
TXT  v=spf1 include:_spf.mx.cloudflare.net ~all
```

세 가지가 다 나온다.

1. **네임서버가 Cloudflare다** → Email Routing·Email Sending 온보딩 가능
2. **MX가 이미 Cloudflare Email Routing을 가리킨다** → 수신 배선이 이미 깔림
3. **SPF가 이미 Cloudflare만 허용한다**

→ 세 번째가 중요하다. 지금 SPF로 `noreply@kpopsoft.com`에서 **Resend로 보내면
SPF가 통과하지 못한다.** Resend를 쓰려면 SPF를 고쳐 Cloudflare와 나란히
등록해야 한다 — 승인 설계를 어기면서 DNS 작업이 늘어난다.

→ 반대로 **Cloudflare로 가면 SPF 작업이 없다.** 이미 맞다.

## 9. Cloudflare 계정 실측 (2026-08-11, 토큰 수령 후)

발급받은 계정 소유 토큰(`cfat_…`)으로 **읽기 전용** 조회한 결과다.

| 확인 | 결과 |
|---|---|
| 토큰 상태 | `/accounts/{id}/tokens/verify` → **200 active** |
| 계정 ID | 유효 (`8c73…170a`) |
| **`kpopsoft@gmail.com`** | **검증 완료 — 2026-07-12T14:34:36Z** ✅ |
| `freestyle926@gmail.com` | 검증 완료 — 2026-07-12T13:57:46Z (오세승) |

→ **미결 2번이 풀렸다.** 설계가 지정한 수신 주소는 이미 검증돼 있다.
무료 조건([02](02-현황분석.md) §8)이 성립한다.

→ 검증 시각이 2026-07-12다. **KPO-23 착수 시작일과 같은 날**이다.
담당자가 그때 여기까지 해 두고 멈춘 것으로 보인다.

**토큰이 못 하는 것** — 아래는 403/빈 결과다.

- 계정 상세 조회 (`Account:Read` 없음)
- zone 목록 (`Zone:Read` 없음) → **Email Routing 규칙을 API로 확인 못 한다**
- 토큰 자신의 권한 조회 (`API Tokens:Read` 없음)

→ 최소 권한 토큰이라는 뜻이고 설계 §7의 방침과 맞다. 다만 그래서
**`inquiry@kpopsoft.com` 라우팅 규칙 존재 여부는 대시보드에서 눈으로 봐야 한다.**

### 발송 API 경로 (공식 문서)

```
POST /accounts/{account_id}/email/sending/send
{ to, from, subject, html, text }
→ delivered / permanent_bounces / queued
```

codex 브랜치가 쓰는 `cloudflare` SDK는 `^7.0.0`이고 npm 최신도 **7.0.0**이다.
버전 조정 없이 그대로 쓸 수 있다.

## 9-1. 테스트 발송 실측 — 응답이 애매하다 (중요)

`inquiry@kpopsoft.com` → `kpopsoft@gmail.com`으로 1통 실제 발송했다.

```
HTTP 200
{"success":true,"errors":[],"messages":[],
 "result":{"message_id":"<j124…@kpopsoft.com>",
           "delivered":[], "queued":[], "permanent_bounces":[]}}
```

**읽을 수 있는 것**

- **토큰에 발송 권한이 있다.** `send`가 200을 냈다. → 미결 4번 해소
- 발신 도메인 `kpopsoft.com`이 거부되지 않았다 — `message_id`가 그 도메인으로 발급됨
- `/email/sending/` 아래 **`send` 외 모든 경로는 404(code 10001)** —
  domains·messages·subscription 전부. 토큰이 `send`만 할 수 있다.
  → **발송 이력을 API로 조회할 방법이 없다.** 대시보드를 봐야 한다.

**세 배열이 전부 비었다 — 그런데 메일은 도착했다** ✅

공식 문서상 `delivered`=즉시 전달, `queued`=지연 예약, `permanent_bounces`=거부다.
**셋 다 빈 경우는 문서에 없다.** 가설이 둘이었다.

1. 전달 판정이 비동기라 응답 시점에는 어느 배열에도 안 들어간다
2. 발신 도메인이 온보딩되지 않아 접수만 되고 실제로는 안 나갔다

**사용자가 `kpopsoft@gmail.com` 수신을 확인했다(2026-08-11). → 1번이 맞다.**

즉 이 계정·이 도메인 조합에서 **정상 발송의 응답 모양이 "세 배열 모두 빈 것"**이다.
`success: true` + `message_id`가 접수의 증거이고, 배열은 나중에 채워지거나
이 경로에서는 아예 안 채워진다.

→ 발신 도메인 온보딩은 **이미 되어 있다.** 추가 작업이 없다.
→ 실측으로 확인된 것은 **접수까지**다. 전달 실패(반송)를 이 응답으로는
   알 수 없다. 반송 추적이 필요하면 대시보드를 봐야 한다.

### ⚠️ 이식할 매퍼가 이 응답을 실패로 판정한다

`cloudflare-email.ts`의 `mapCloudflareEmailResponse()`는 이렇게 짜여 있다.

```ts
if (delivered.length > 0)         return { ok: true, … };
if (permanent_bounces.length > 0) return { ok: false, errorCode: "permanent_bounce" };
if (queued.length > 0)            return { ok: false, errorCode: "queued" };
return { ok: false, errorCode: "provider_error" };   // ← 지금 응답이 여기로 간다
```

**메일이 도착했는데도 코드는 `provider_error`로 기록한다.** 실측으로 확인됐다.
D5(실패를 보이게 한다)를 켜면 성공할 때마다 실패 로그가 쌓인다 —
"조용한 실패"의 정반대인 **거짓 실패**다. 둘 다 나쁘다.

→ **매퍼를 고쳐서 이식한다.** [03](03-원인과-결정.md) D7.

> codex 브랜치의 `tests/cloudflare-email.test.mts`는 이 매퍼를 통과시킨다.
> 가짜 응답으로만 돌았고 **실제 응답 모양을 본 적이 없기 때문**이다.
> 테스트가 초록이라는 게 맞다는 뜻이 아니라는 사례로 남긴다.

## 10. 왜 여태 몰랐나

- 사용자에게는 성공 화면이 뜬다. 폼 입장에서는 **실제로 성공**이다 — 저장됐으니까.
- 실패 신호가 `console.info` / `console.error`뿐이다.
- 문서는 정직하게 적어 뒀다 — `docs/07-dev/02-개발상태.md:99-100`
  "이메일은 코드만 있고 실제 발송은 `RESEND_API_KEY` 유무에 달려 있습니다."
  다만 그게 **"지금 안 나가고 있다"로 읽히지 않는다.**
- 그리고 main의 Resend 코드 자체가 **승인 설계와 다른 물건**이라,
  키를 채웠어도 KPO-23을 만족하지 못했다.
