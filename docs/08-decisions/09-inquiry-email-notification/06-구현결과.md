## 계획과 다른 점

### 1. `cloudflare` SDK 대신 `fetch`를 썼다 ⚠️

승인 설계 §7은 **"공식 `cloudflare` Node SDK의 `client.emailSending.send()`"**를
지정했다. 실제로는 `fetch`로 REST를 직접 호출했다.

**이유** — REST 경로(`POST /accounts/{id}/email/sending/send`)를 이미 실측으로
검증했고, POST 하나에 의존성을 하나 더 얹을 이유를 못 찾았다.

**되돌리기 쉽다** — `sendInquiryEmail()` 안의 `fetch` 블록만 SDK 호출로
바꾸면 된다. 시그니처와 판정 로직은 그대로다.

→ **설계에서 벗어난 부분이라 사용자 판단이 필요하다.** SDK를 쓰는 쪽이
맞다면 바꾼다.

### 2. 응답 매퍼를 고쳤다 (D7 — 계획대로)

이식 원본은 세 배열이 전부 빈 응답을 `provider_error`로 떨어뜨렸는데,
**그게 이 계정의 정상 응답 모양이었다.** 그대로 뒀으면 성공할 때마다
거짓 실패 로그가 쌓였다.

판정을 **접수 여부**(`success` + `message_id`)로 옮기고
`permanent_bounces`만 실패로 잡는다. 근거는 [03](03-원인과-결정.md) D7.

### 3. `mapCloudflareEmailResponse` 시그니처가 바뀌었다

`(response, httpOk, apiSuccess)`로 인자가 늘었다. 판정에 HTTP 상태와
`success` 플래그가 필요해서다. 원본은 `response` 하나만 받았다.

### 4. `resend` 의존성은 아직 안 뺐다

코드 참조는 전부 제거했지만(`grep`으로 확인) `package.json`에는 남아 있다.
[03](03-원인과-결정.md) §5-6이 미결이라 손대지 않았다.
