# 04 — 구현계획

근거는 전부 [03-원인과-결정](03-원인과-결정.md)에 있다.

## 순서와 그 이유

**Cloudflare 설정(0~2단계)이 코드(3~4단계)보다 먼저다.**
이식할 코드는 이미 검증된 것이라 리스크가 낮은 반면, 막히면 막히는 곳은
**Cloudflare 쪽**이다 — destination 검증, 토큰 권한, 베타 제약.
설정을 먼저 세워야 코드를 **실제로 메일이 오는 상태에서** 검증할 수 있다.

### 0단계 — 전제 확인 (일부 완료)

**✅ 끝난 것** ([02](02-현황분석.md) §9)

- Cloudflare 토큰 수령 → `.env.local`에만 기록. 상태 **active**
- `kpopsoft@gmail.com` **Destination Address 검증 완료**(2026-07-12)
- 발송 경로 확인: `POST /accounts/{id}/email/sending/send`
- `cloudflare` SDK `^7.0.0` = npm 최신. 버전 조정 불필요
- 발송 수단 Cloudflare 확정 (사용자 확답)

**남은 것**

- **Vercel** → Settings → Environment Variables에서 `RESEND_API_KEY` 유무 확인.
  [02](02-현황분석.md) §3은 정황 추정이다. 추정 위에 작업하지 않는다.
  - 이미 설정돼 있다면 → 원인이 다르다. Vercel 함수 로그에서 `[email]`을
    검색해 실제 실패 사유를 찾고 이 계획을 다시 쓴다.
- **Email Sending 베타 제약 재확인** — 설계 §7이 요구한 항목이다.

### 1단계 — Cloudflare 수신 (D6)

DNS·검증은 이미 서 있다. 남은 것만 한다.

1. ~~Destination address 검증~~ — **완료**(2026-07-12)
2. **Routing rule: `inquiry@kpopsoft.com` → `kpopsoft@gmail.com`**
   — 토큰에 `Zone:Read`가 없어 API로 확인 못 했다. **대시보드에서 확인/생성**
3. `inquiry@kpopsoft.com`으로 외부에서 한 통 보내 Gmail 도착 확인

### 2단계 — 발송 권한 확인

토큰이 활성인 것은 확인했지만 **`Email Sending: Edit` 보유 여부는 모른다**
— 읽기용 엔드포인트가 없다([02](02-현황분석.md) §9).

1. `POST /accounts/{id}/email/sending/send`로 **테스트 1통** 발송
   (`inquiry@kpopsoft.com` → `kpopsoft@gmail.com`)
2. 403/10001이 나오면 대시보드에서 권한 추가 또는 토큰 재발급
   — 권한은 **`Email Sending: Edit`만** 준다(최소 권한, 설계 §7)
3. **토큰·계정 ID를 코드·테스트·로그·OpenProject에 적지 않는다** (설계 §7)

> 이 한 통이 D2 전체의 성립 여부를 가른다. 코드를 옮기기 전에 먼저 친다 —
> 권한이 없으면 이식한 코드가 전부 `unauthorized`로 떨어질 뿐이다.

### 3단계 — 코드 이식 (D4)

`origin/codex/kpopsoft-maxonomy-concept-wind`에서 가져온다.

```
src/lib/inquiries/email-message.ts        ← 그대로
src/lib/integrations/cloudflare-email.ts  ← DeliveryAttempt 추가 후
tests/inquiry-email-message.test.mts      ← 참고해 이식
tests/cloudflare-email.test.mts           ← 참고해 이식
```

같이 할 일.

- `src/lib/admin/types.ts`에 `DeliveryAttempt` 추가
  (`{ ok: boolean; externalId?: string; errorCode?: string }`)
- `package.json` — `cloudflare` 추가, `resend` 제거([03](03-원인과-결정.md) §5-4 확답 후)
- `src/lib/email.ts` — `notifyNewInquiry()`가 `sendInquiryEmail()`을 부르게 교체.
  **호출부 시그니처는 유지한다** — `inquiry-actions.ts:132-137`을 안 건드리려고.

**폼·저장 경로는 건드리지 않는다**(D1).

### 4단계 — 실패 노출 (D5)

| 위치 | 바꿀 것 |
|---|---|
| 설정 누락 | `configuration_error` → `console.warn`(운영은 `error`) + 문의 id |
| `queued` / `permanent_bounces` | **실패로 로그.** `delivered`가 비면 성공이 아니다 |
| `unauthorized` / `throttled` / `provider_error` | 같은 형식으로 통일 |

형식: `[email] 문의 알림 미발송 — <errorCode> (inquiry <id>)`

호출부의 best-effort try/catch는 **그대로 둔다** — "저장은 성공 처리"라는
기준(`docs/06-admin/03…:47`)을 지키는 장치다.

### 5단계 — 로컬 실발송 확인

`.env.local`을 채운다.

```
CLOUDFLARE_API_TOKEN=...
CLOUDFLARE_ACCOUNT_ID=...
INQUIRY_NOTIFICATION_FROM=inquiry@kpopsoft.com
INQUIRY_NOTIFICATION_TO=kpopsoft@gmail.com
```

`npm run dev` → 홈 Contact에서 실제 제출 → `kpopsoft@gmail.com` 수신 확인.

> ⚠️ **로컬과 운영이 같은 Supabase를 공유한다**(`.env.example` 머리말).
> 여기서 넣은 테스트 문의는 **운영 DB에 그대로 쌓인다.**
> 확인 후 `/admin/inquiries`에서 정리한다.

> ⚠️ 수신자는 검증된 주소뿐이라 **로컬 테스트도 `kpopsoft@gmail.com`으로 간다.**
> 본인 주소로 돌리려면 그 주소를 Cloudflare에서 먼저 검증해야 한다(D3).
