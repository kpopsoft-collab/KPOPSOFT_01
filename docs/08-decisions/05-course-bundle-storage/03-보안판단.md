## 1. 새 탭이 왜 괜찮은가 (D2)

번들 HTML은 `https://oxkxkqfwliobkyyexjtk.supabase.co/storage/v1/object/public/...`
에서 열린다. 그 안의 스크립트는 **그 origin에서 실제로 실행된다.**
`sandbox` iframe이었다면 opaque origin이라 실행돼도 아무 데도 못 닿지만,
새 탭에는 그 보호가 **없다.** 그래서 "그 origin에 훔칠 게 있는가"를 따진다.

| 노리는 것 | 가능한가 | 왜 |
|---|---|---|
| 어드민 세션 토큰 | **아니오** | supabase-js는 세션을 앱 origin(`www.kpopsoft.com`)의 localStorage에 `sb-<ref>-auth-token`으로 둔다. supabase.co에서 못 읽는다 |
| 쿠키를 실은 API 호출 | **아니오** | Supabase는 Bearer 토큰 방식이다. 쿠키가 자동으로 실리지 않는다 |
| Supabase REST API 호출 | 가능하지만 **의미 없음** | anon 키로 되는 일뿐이다. anon 키는 `NEXT_PUBLIC_`으로 이미 공개이고 CORS도 열려 있어 아무 사이트에서나 된다. 새로 얻는 권한이 0 |
| 다른 과정의 번들 읽기 | 가능하지만 **의미 없음** | 어차피 공개 버킷이다 |
| Service Worker 등록 | 범위 제한적 | SW 스코프는 스크립트 경로 이하로 제한된다. `Service-Worker-Allowed` 헤더가 없으면 그 폴더 밖으로 못 나간다 |

### 1-1. 결정적인 것 — 이건 UGC가 아니다

업로드할 수 있는 건 `public.is_admin()`을 통과한 **KPOPSOFT 내부 인원**뿐이다
([04](04-데이터모델-DDL.md) §2의 정책). 익명 사용자가 올리는 콘텐츠가 아니다.

결정기록 01의 정제 파이프라인도 사실 "공개 입력 방어"가 아니라 "어드민 계정
탈취 시 피해 축소"였다. 위협 모델이 원래 가볍다.

### 1-2. 새 탭으로 얻는 것

iframe을 버리면서 **iframe의 최대 비용이 통째로 사라진다.**

- **SEO** — iframe 내용은 부모 페이지 콘텐츠로 색인되지 않는다. 상세 페이지
  본문이 우리 데이터로 남으므로 이 손실이 없다
- **높이** — cross-origin iframe은 부모가 내용 높이를 모른다. 고정 높이면
  이중 스크롤이 되고, 자동 높이는 업로드 문서에 postMessage 스크립트를
  심어야 한다. 둘 다 사라진다
- **디자인 일관성** — 한 페이지 안에 두 개의 디자인이 공존하지 않는다

## 2. 왜 Supabase Storage인가 (D1)

| | Supabase Storage | Cloudflare R2/Pages |
|---|---|---|
| 업로드 코드 | `image-upload.tsx` 패턴 재사용 | 새로 작성 |
| 인증·권한 | 기존 `is_admin()` RLS 그대로 | 토큰 별도 발급·보관 |
| 벤더 | 추가 없음 | +1 (계정·배포·삭제정책 전부 신규) |
| 얻는 것 | — | 별도 origin, 저렴한 egress |

Cloudflare의 실질 이득은 **별도 origin** 하나인데, §1에서 봤듯 그 origin에
훔칠 게 없어서 이득이 크지 않다. egress 비용은 아직 그 논의를 할 규모가 아니다.

### 2-1. 공개 버킷은 편의가 아니라 **요구사항**이다

서명 URL(`createSignedUrl`)로는 안 된다. `index.html` 안의
`<img src="images/a.png">`는 **상대경로라 서명 토큰을 물고 가지 못한다.**
서브 리소스가 전부 깨진다. 게다가 서명은 만료되므로 상세 페이지에 박아 둘
링크로 쓸 수 없다.

→ `public = true` 버킷.

### 2-2. 우리 도메인으로 프록시하면 안 된다 (D4)

`oxkxkqfwliobkyyexjtk.supabase.co/...` URL이 지저분해서 `kpopsoft.com/...`으로
감싸고 싶어질 것이다. **그러면 §1의 표가 통째로 뒤집힌다.**

어드민 세션이 있는 곳이 바로 그 origin이다. 임의 HTML을 **유일하게 위험한
곳으로 옮기는** 셈이다. Next 라우트 핸들러로 스트리밍하든 rewrite를 걸든
결과는 같다.

예쁜 URL이 정말 필요하면 **별도 서브도메인**(`course.kpopsoft.com`)을 파야
한다. 지금은 범위 밖이다([01](01-요구사항.md) §5).

## 3. zip을 어디서 푸는가 (D3)

| 방식 | 새 공격면 | 실패 모드 | 판단 |
|---|---|---|---|
| 폴더 업로드(`webkitdirectory`) | 없음 | 부분 업로드 | 안전하지만 어드민이 미리 압축을 풀어야 한다 |
| **zip + 어드민 브라우저에서 해제** | zip 파서(어드민 브라우저) | zip bomb → 자기 탭 OOM | **채택** |
| zip + 서버에서 해제 | zip 파서(우리 서버) + service_role | 서버 OOM, 경로 탈출 | **금지** |

서버 해제는 두 번 탈락한다 — 우리 자원을 태우고, `bodySizeLimit: "2mb"`
(`next.config.ts:17`)라 이미지 든 zip은 시작도 못 한다.

폴더와 브라우저 zip의 **실질 보안 차이는 하나뿐**이다. zip 파서는 어드민
자기 브라우저에서 자기가 고른 zip을 여는 구조라 "악성 zip = 자해"이고 위협이
아니다. 다만 **엔트리 이름은 신뢰할 수 없다** — `webkitRelativePath`는
브라우저가 만들어 주지만 zip 엔트리 이름은 파일 안에 적힌 임의 문자열이다.

### 3-1. 엔트리 경로 검증 (필수)

zip 엔트리 이름을 그대로 Storage 키에 붙이면 `../../other/index.html` 같은
이름이 의도한 prefix 밖으로 쓴다. 아래를 **전부** 거른다.

```
거부: 세그먼트에 ".." 또는 "." 이 있음
거부: "/" 로 시작 (절대경로)
거부: "\" 포함 (윈도 경로)
거부: "C:" 등 드라이브 문자
거부: 널바이트(\0) 포함
거부: 빈 세그먼트("a//b")
거부: "#" "?" "%" 포함 — supabase-js가 경로를 인코딩하지 않아 URL에서 잘린다
거부: 허용 확장자 밖 (§4)
무시: "__MACOSX/" 하위, ".DS_Store", "Thumbs.db", "." 로 시작하는 디렉터리
```

서버 액션에서 한 번 더 막는다 — 폼이 보낸 `path`가
`^[0-9a-f-]{36}/$` 모양이 아니면 거부한다. DB에도 같은 CHECK를 건다
([04](04-데이터모델-DDL.md) §1). **삭제 루틴이 임의 prefix를 지우지 못하게
하는 것이 목적이다.**

### 3-2. 파일명 인코딩 — 조용히 깨지는 지점

zip 엔트리 이름의 인코딩은 보장되지 않는다.

- macOS에서 만든 zip은 한글 파일명을 **NFD(분해형)** 로 저장한다. HTML 안의
  참조는 보통 **NFC(결합형)** 라 → 이미지 404
- 윈도 압축 프로그램은 UTF-8 플래그 없이 **CP949**로 넣기도 한다 → 글자 깨짐

우리가 HTML 본문을 고쳐 쓰지 않으므로 엔트리 이름만 정규화해도 완전히
맞출 수 없다. → **파일명에 ASCII 밖 문자가 있으면 경고를 띄운다.**
막지는 않되 "이미지가 안 보이면 파일명을 영문으로 바꿔 다시 올려 주세요"를
알려 준다.

## 4. 확장자 허용목록 (D7)

```
html htm css js mjs json
png jpg jpeg webp gif svg ico avif
woff woff2 ttf otf
```

- **`.svg`는 그 자체로 스크립트를 실행할 수 있는 포맷이다.** 허용하되
  **알고 허용한다** — 격리된 origin이고 업로더가 관리자다
- **`.js`도 같은 근거로 허용한다.** §1의 전제(그 origin에 훔칠 게 없다)가
  깨지는 순간 — 즉 D4를 어기고 우리 도메인으로 옮기는 순간 — 이 결정을
  다시 봐야 한다
- 목록 밖은 조용히 건너뛰지 않고 **이름을 찍어 거부**한다. 빠진 파일 때문에
  화면이 깨졌을 때 원인을 알 수 있어야 한다

### 4-1. Content-Type을 파일마다 명시한다

Storage는 업로드 때 준 `contentType`을 그대로 되돌려준다. 안 주면
`application/octet-stream`이 되어 **브라우저가 렌더 대신 다운로드한다.**
확장자 → MIME 맵을 클라이언트에 두고, 버킷의 `allowed_mime_types`와
**정확히 같은 집합**으로 맞춘다. 어긋나면 업로드가 원인 모를 오류로 실패한다.

## 5. 폴더 키 (D8)

`education/<uuid>/…` — 클래스 id가 아니라 **업로드마다 새로 만드는 UUID**.

- 새로 만드는 화면에는 **클래스 id가 아직 없다.** id 기반이면 임시 폴더에
  올렸다가 옮겨야 하는데, Storage `move()`는 객체 단위라 파일 수십 개면 비싸다
- 교체하면 새 UUID 폴더가 생기므로 **CDN 캐시 문제가 없다.** 별도 버전
  세그먼트가 필요 없다
- `image-upload.tsx:58`이 이미 UUID 키를 쓴다 — 새 관행이 아니다

**옛 폴더 삭제는 저장이 성공한 뒤 서버가 한다.** 업로드 시점에 지우면
편집을 취소했을 때 살아 있는 번들이 사라진다.

## 6. CSP(G6)와의 관계

이 작업은 CSP 상황을 **나쁘게 만들지 않는다.**

번들은 우리 페이지에 아무것도 심지 않는 바깥 링크다. `frame-src`도
`script-src`도 늘어나지 않는다. G6가 여전히 걸려 있는 이유는
`detail_html`의 인라인 `<style>` 하나뿐이고, 그건 결정기록 01에서 온 것이다.

| 번들 내용이 검색에 색인되지 않는다 | 감수. 본문이 우리 페이지에 남는다(§1-2) |
