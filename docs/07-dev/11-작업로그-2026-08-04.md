# 작업로그 2026-08-04 — 과정 상세 번들(zip) Storage 업로드

백로그 [05-course-bundle-storage](../../backlogs/05-course-bundle-storage/00-START-HERE.md)
구현. 정규 클래스 상세 자료를 **여러 파일 묶음(zip)** 으로 올려 Supabase Storage에
두고, 상세 페이지에서 **새 탭 링크**로 연다.

> **코드만 끝났다. DB는 아직이다.** 마이그레이션
> `20260804090000_course_bundle_storage.sql`은 작성만 됐고 **사용자가 실행해야**
> 한다. 실제 동작 확인은 그 뒤다.

## 왜 필요했나

`detail_html`(2026-08-03, [10-작업로그](10-작업로그-2026-08-03.md))은 `.html` **한 장**만
받는다. 실제 상세 자료는 이미지·CSS·서브 페이지가 같이 오는데, 텍스트 컬럼 하나로는
`<img src="images/a.png">`가 **가리킬 대상 자체가 없다.** 정제기가 태그를 지우는
문제가 아니라 원리적으로 불가능하다.

## 무엇이 생겼나

| 층 | 내용 |
|----|------|
| DB | `education_regular_classes`에 `detail_bundle_path`·`detail_bundle_name` + 경로 CHECK |
| DB | Storage 버킷 `class-bundles` (public, 10MB/객체, MIME 15종) + 정책 4건 |
| 순수 | `src/lib/admin/course-bundle.ts` — zip 엔트리 검증·정규화, 폴더 재귀 순회 (테스트 34건) |
| 어드민 | `BundleUpload` 위젯 — 브라우저에서 zip 해제 후 파일별 업로드 |
| 어드민 | `BundleIntent`(keep/replace/remove) + 저장 성공 뒤 옛 폴더 삭제 |
| 공개 | `/education/programs/[slug]`에 "과정 상세 자료" 새 탭 링크 블록 |

의존성 `fflate@^0.8.3` 추가(브라우저 전용).

## 왜 이렇게 했나 (판단 근거)

전문은 [03-보안판단.md](../../backlogs/05-course-bundle-storage/03-보안판단.md)에 있다. 요지만.

### iframe이 아니라 새 탭

sandbox iframe이었다면 opaque origin이라 안전했는데 새 탭에는 그 보호가 없다.
그래서 "그 origin에 훔칠 게 있는가"를 따졌다 — **없다.** supabase-js는 세션을
**앱 origin**(`www.kpopsoft.com`)의 localStorage에 두고, Supabase는 쿠키가 아니라
Bearer 토큰을 쓴다. anon 키는 이미 `NEXT_PUBLIC_`으로 공개이고 CORS도 열려 있어
새로 얻는 권한이 0이다. 대신 iframe의 비용(SEO 손실, 높이 문제, 디자인 이중화)이
통째로 사라진다.

### 그래서 **우리 도메인으로 프록시하면 안 된다**

`kpopsoft.com/...`으로 감싸는 순간 위 판단이 통째로 뒤집힌다 — 어드민 세션이 있는
바로 그 origin으로 임의 HTML을 옮기는 셈이다. 예쁜 URL이 필요하면 별도 서브도메인을
파야 한다. 링크 URL이 `*.supabase.co`인지가 곧 이 결정의 검증 항목이다.

### 공개 버킷은 편의가 아니라 요구사항

서명 URL로는 안 된다. `index.html` 안의 `<img src="images/a.png">`는 **상대경로라
서명 토큰을 물고 가지 못해** 서브 리소스가 전부 깨진다. 게다가 서명은 만료된다.

### zip은 어드민 브라우저에서 푼다

서버 해제는 두 번 탈락한다 — 우리 자원을 태우고, `bodySizeLimit: "2mb"`라 이미지
든 zip은 시작도 못 한다. 브라우저 해제의 유일한 실질 위험은 **zip 엔트리 이름이
신뢰할 수 없는 문자열**이라는 것뿐이라(`../../evil.html`), 클라이언트 거부 규칙 +
서버 액션 정규식 + DB CHECK **3중**으로 막았다.

### 폴더 키는 클래스 id가 아니라 UUID

새로 만드는 화면에는 클래스 id가 아직 없다. 교체하면 새 UUID 폴더가 생기므로
CDN 캐시 문제도 같이 사라진다.

### 삭제 순서를 뒤집으면 안 된다

`get(id)`로 옛 경로 확보 → DB update → **성공한 뒤에만** 옛 폴더 삭제.
먼저 지웠다가 update가 실패하면 화면에는 살아 있는 번들이 Storage에서만 사라진다.
이 순서면 최악이 고아 폴더이고, 그건 무해하다.

## 리뷰에서 잡은 것

- `supabase-js`의 `storage.list()` **기본 limit이 100**이다. 옵션 없이 부르면 한
  폴더에 100개가 넘을 때 나머지가 **조용히 안 지워진다.** `{ limit: 1000 }`을 넣었다
- `list()`는 재귀가 아니고 하위 폴더는 `id === null`로 온다 — `images/`까지 지우려면
  순회가 필요하다. 리포에 인라인으로 두면 테스트가 안 되므로 lister를 주입받는
  순수 함수(`walkBundle`)로 뽑았다

## ⚠️ 배포 순서 — DDL이 먼저다

컬럼 없는 DB에서 이 코드가 돌면 **어드민 정규 클래스 목록이 500이 되고, 저장도
`PGRST204`로 실패한다**(어드민 select 컬럼이 `FIELDS`에서 자동 파생되기 때문).
공개 상세는 조용히 정적 폴백으로 떨어져 **옛 데이터가 그대로 보인다** — 이쪽이
더 알아채기 어렵다. 공개 목록은 상세 전용 컬럼을 공통 상수에서 뺐기 때문에 영향이 없다.

로컬이 곧 운영이라 **지금 이 작업 트리 상태가 그렇다.**

## 교차검증에서 나와 고친 것

- **엔트리 이름의 `#`·`?`·`%` 거부.** supabase-js는 업로드 경로를 인코딩하지 않고
  URL에 그대로 붙인다 — `guide #2.png`는 `#` 뒤가 프래그먼트로 잘려 **다른 키로
  조용히 올라가고** 위젯은 성공을 띄운다. 이미지만 404가 난다
- **업로드 중 저장 잠금.** 진행 중에 저장하면 intent가 아직 `keep`이라 컬럼은 안 붙고
  올라간 파일 수십 개만 고아로 남는다
- **업로드 워커의 예외 처리.** 밖으로 새면 남은 워커가 뒤에서 계속 돌며 진행 표시를
  되살린다
- **`detail_bundle_path`를 공통 컬럼 상수에서 빼 상세 쿼리에만 붙였다** — 목록이
  쓰지도 않는 컬럼 때문에 `/education`까지 같이 폴백으로 떨어질 이유가 없다
