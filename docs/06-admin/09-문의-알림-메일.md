# 09. 문의 알림 메일 — 지금 어떻게 동작하나

새 문의가 저장되면 관리자에게 알림 메일이 나간다.
**발송은 Cloudflare Email Service로 한다 — Resend가 아니다.**

기준 작업은 OpenProject
[KPO-23 "이메일 발송시스템 개발"](https://op.kpopsoft.com/work_packages/182)이고,
왜 그렇게 정했는지는
[결정 기록 09](../08-decisions/09-inquiry-email-notification/00-START-HERE.md)에 있다.

## 1. 경로

```
홈 Contact 폼 / education 문의 폼
  → submitInquiry()          src/lib/inquiry-actions.ts   (Server Action)
  → getAdminData().createInquiry()                        Supabase 저장
  → notifyNewInquiry()       src/lib/email.ts
  → sendInquiryEmail()       src/lib/integrations/cloudflare-email.ts
  → buildInquiryEmail()      src/lib/inquiries/email-message.ts
  → POST https://api.cloudflare.com/client/v4
         /accounts/{id}/email/sending/send
```

두 폼(`sections/final-cta.tsx`, `sections/education/inquiry-form.tsx`)이
**같은 Server Action을 쓴다.** 한쪽만 고치는 일은 없다.

## 2. 저장과 발송은 분리돼 있다

**발송이 실패해도 문의 저장은 성공 처리한다**(§7 기준).
문의자에게는 접수 완료 화면이 그대로 뜬다 — 실제로 접수됐기 때문이다.
우리 쪽 메일 사정으로 실패를 알리면 재제출을 유도해 중복 문의만 쌓인다.

> **그래서 메일은 보조 경로다. 1차 확인처는 `/admin/inquiries`다.**
> 메일이 끊겨도 문의는 잃지 않는다.

`sendInquiryEmail()`은 **예외를 던지지 않는다.** 항상 `DeliveryAttempt`
(`{ok, externalId?, errorCode?}`)를 돌려준다.

## 3. 환경변수 — 운영에서는 필수다

| 변수 | 값 |
|---|---|
| `CLOUDFLARE_API_TOKEN` | 권한은 `Email Sending: Edit`만 (최소 권한) |
| `CLOUDFLARE_ACCOUNT_ID` | |
| `INQUIRY_NOTIFICATION_FROM` | `inquiry@kpopsoft.com` |
| `INQUIRY_NOTIFICATION_TO` | `kpopsoft@gmail.com` — **Cloudflare에서 검증된 주소** |
| `NEXT_PUBLIC_SITE_URL` | 선택. 메일 속 어드민 링크용, 없으면 `https://kpopsoft.com` |

하나라도 비면 `configuration_error`로 발송을 건너뛴다.
**저장은 여전히 성공하므로 폼은 정상으로 보인다** — 이 조합이
2026-07~08에 두 달간 알림을 죽여 놓고도 아무도 모르게 만들었다
(OpenProject [WP 258](https://op.kpopsoft.com/work_packages/258)).

### 수신자를 늘리려면 Cloudflare에서 먼저 검증한다

**검증된 수신 주소로 보내는 메일만 전 플랜 무료**이고, 임의 수신자로
넓히면 Workers 유료 플랜이 필요하다. 그래서 `INQUIRY_NOTIFICATION_TO`에
검증 안 된 주소를 넣으면 조용히 실패하거나 과금 구조가 바뀐다.

`admin_users` 테이블로 **폴백하지 않는다.** 그 테이블은 로그인 권한
목록이지 알림 수신 목록이 아니다 — 관리자가 늘 때마다 수신자가 말없이
따라 늘면 곤란하다.

## 4. 메일 내용

`buildInquiryEmail()`이 만든다.

- 제목 — `[KPOPSOFT] 새 문의: <유형> · <세부 유형>`
- **HTML 본문과 텍스트 대체본을 둘 다** 넣는다
- 유형·보낸 사람·연락처·접수 시각·문의 내용
- **어드민 상세 링크** `/admin/inquiries/<id>`
- 연락처가 유효한 이메일일 때만 `reply_to` — 메일에서 바로 답장하면 문의자에게 간다

## 5. 응답 판정 — `delivered`가 비어도 성공이다

Cloudflare 응답은 `message_id`와 `delivered`·`queued`·`permanent_bounces`
배열을 준다. **정상 발송에서도 세 배열이 전부 비어 있다**(2026-08-11 실측,
수신 확인함).

그래서 판정 기준은 **접수 여부**다.

| 응답 | 판정 |
|---|---|
| `permanent_bounces` 있음 | 실패 — `permanent_bounce` |
| HTTP 200 + `success:true` + `message_id` | **성공(접수됨)** |
| 401 / 403 | 실패 — `unauthorized` |
| 429 | 실패 — `throttled` |
| 그 외 | 실패 — `provider_error` |

> ⚠️ `ok: true`는 **제공자가 접수했다**는 뜻이지 수신함에 꽂혔다는 뜻이 아니다.
> 이 API로 확인할 수 있는 범위가 거기까지다. 최종 전달 추적이 필요하면
> Cloudflare 대시보드를 본다.

## 6. 실패는 반드시 로그에 남는다

```
[email] 문의 알림 미발송 — <errorCode> (inquiry <id>)
```

운영(`NODE_ENV=production`)에서는 `console.error`, 그 외에는 `console.warn`.
**문의 id를 같이 남기는 이유** — 그 id로 `/admin/inquiries`에서 해당 건을
찾아 수동으로 대응할 수 있다.

성공하면 `[email] 문의 알림 접수됨`에 `messageId`를 남긴다.

> 예전에는 이 자리가 `console.info` 한 줄이었다. 그래서 기능이 죽은 것을
> 두 달 동안 아무도 몰랐다. **미발송은 info로 남기지 않는다.**

## 7. 수신 — `inquiry@kpopsoft.com`

`kpopsoft.com`의 NS·MX·SPF가 이미 전부 Cloudflare다.
Email Routing으로 `inquiry@kpopsoft.com`을 `kpopsoft@gmail.com`으로 전달한다.
설정은 Cloudflare 대시보드에서 하고 저장소 코드와 무관하다.

## 8. 범위 밖

- **방문자에게 보내는 접수 확인 메일** — 임의 수신자 발송이라 무료 범위를
  벗어난다. 승인 설계가 명시적으로 제외했다.
- **실패 재시도 큐** — 문의량이 월 몇 건 수준이라 과하다. 필요하면
  어드민의 수동 재시도로 붙인다.
